---
title: "AWS 介绍面向用户开放 AgentCore Runtime 的两种架构"
dek: "AWS 介绍了两种接入架构，分别以不同方式向智能体运行环境传递用户身份。运营方仍需检查自身配置。"
---

AWS 于 2026 年 11 月 17 日发布指南，介绍如何通过网页或移动应用向用户开放 Amazon Bedrock AgentCore Runtime。文章给出两种架构，用于验证请求并将用户身份传递给智能体，同时指出应用运营方负责构建接入层。[^1]

AWS 表示，AgentCore Runtime 会为每个会话启动一个独立的 microVM。该文章将执行环境与接入路径区分开来：运营方需要决定谁可以访问运行环境、验证请求，并在整个调用链中保留用户身份。指南还要求实施授权、各环节最小权限、网络控制和内容筛查，并记录身份验证及工具授权决策。[^1]

第一种方案由 Amazon API Gateway 接收请求。Lambda 授权器检查 Cognito 签发的令牌，Lambda 代理则通过虚拟私有云端点将令牌转发给运行环境。AWS 描述了一种会话标识符：将用户标识与客户端提供的会话 ID 组合起来；文章还建议在生产部署前配置 AWS WAF 规则。[^1]

第二种方案由 AgentCore Gateway 验证传入令牌。Lambda 拦截器提取用户身份声明，网关再获取机器对机器令牌，用于调用运行环境。AWS 表示，运行环境会检查工作负载令牌；对于无人值守任务，会话上下文密钥可以携带受限的身份快照。这些是 AWS 指南中的架构和安全主张；保存的文章不能确定某个具体部署的配置。[^1]

:::analysis
这一问题涉及智能体层（T5）和运行时层（T2）：前者关系到用户请求中的身份与工具权限，后者关系到会话和访问配置。因此，除非用户或核验者能够检查相关证据，否则仍需信任运营方的实现。这里关注的可核验属性是可识别性：如果服务某个用户的确切版本和配置有记录且可供检查，该用户就能判断自己是否受到相关问题的影响。运营方和用户应对照指南检查自身的身份传递、权限、接入控制和日志；保存的来源没有推荐任何修复版本。[^1]
:::
